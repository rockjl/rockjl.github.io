13:T18d78,<h1>内存泄露</h1>
<p>首先我们先来讲内存泄露，rust中有两种方式可以造成内存泄露。</p>
<ul>
<li>循环引用
如下的代码执行之后我们在控制台与系统监视器中监控进程执行过程，测试路程如下。</li>
</ul>
<ol>
<li>首先在控制台打印main function start的时候内存还未分配太多，索引进程占用内存还是很小的。</li>
<li>等到空太太打印start add mem以后，可以看到系统监视器中进程内存占用增加到了30多MB。</li>
<li>但是看到outside stack_alloc打印到控制台的时候并未在系统监视器中看到内存的释放，代表内存泄露了，并且drop函数也并未执行。
总结：本来在函数mem_alloc执行过后就应该回收内存了，第一：栈空间的回收，第二：堆空间的回收。由于我们使用了智能指针，内存大多分配在了堆空间，但是堆空间未回收是因为出现了循环引用。当我们把其中<code>cur_node.borrow_mut().next = Some(first_node.clone());</code>注释掉再次执行的时候就会看到内存的释放了</li>
</ol>

<h1>内存分配</h1>
<p>当然这里也不用多说，rust的内存分配大家都知道分为堆和栈两种。</p>
<ul>
<li>堆
堆空间的内存分配需要使用智能指针的配合。像是Vec和String都是存储在堆中。</li>
<li>栈
对于栈的分配我们需要来讲一讲。栈空间是有限的，为什么说有限，是因为栈空间是在当前线程的执行堆栈中分配内存，受限于当前线程的堆栈大小。(线程的默认堆栈大小可以直接修改操作系统的参数，如果是我们自己启动的线程可以在线程启动之前来修改)。
包括数组的初始化，我们可以发现rust对于数组的初始化，如果想在栈空间初始化过大的数组是一件很累的事情。如果手动在栈空间写出来了一个超大的数组，并且大小超过了当前线程执行的堆栈大小，进程在执行到需要在线程堆栈非配大量内存的函数的时候，在这个函数的位置会报错(注意：这里不是panic。是报错：EXC_BAD_ACCESS(code=2, address=0x7ff7bf700600。我的是mac，其他的操作系统错误也只是大同小异罢了。下面代码如果在某些人电脑上面没有出现错误，可以复制大量的new_obj代码行。一定会出现的。))。</li>
</ul>

<h2>总结</h2>
<ol>
<li>栈内存的分配是在函数调用的时候，函数那需要多大的栈空间那么就需要申请多大的内存空间。注意这里是函数调用的时候，而不是代码块调用的时候。</li>
<li>栈内存的回收是在堆栈所在线程销毁的时候。不管在控制台查看还是在系统监视器中查看，都是这个结果。</li>
<li>堆内存的分配是在代码调用的时候，准确的说是哪里调用了代码哪里就分配了内存。</li>
<li>堆内存的释放是在数据所有者所在作用于结束的时候即刻回收内存。</li>
<li>如果使用了std::mem::ManuallyDrop。栈内存还是在线程销毁的时候回收内存。堆空间内存则会造成泄露。</li>
<li>注意：数据不管是在堆还是在栈，被回收的内存都有可能处于无法访问的状态。有些同学尝试使用unsafe访问被回收的内存地址，如果数据在栈，并且当前线程还未销毁的情况下，还不会有问题。但是如果数据在堆，就很有可能会报错。造成程序的终止</li>
