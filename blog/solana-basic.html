Solana八大核心概念

  1. 历史证明---PoH

    • 核心定位：加密时间基准，解决区块链节点时间同步瓶颈
    • 地层逻辑：通过链式哈希生成不可篡改时间序列，为每笔交易分配为一可信时间戳，节点无需频繁通信即可独立验证交易顺序，是高频并发的基础

  2. 塔式拜占庭容错---TowerBFT

    • 核心定位： 优化版共识协议，基于PoH实现高效共识。

    • 地层逻辑：复用PoH时间序列，记录节点投票历史，减少全量交易链验证需求，兼顾去中心化、安全性与共识效率，值乘网络稳定达成一致。

      TowerBFT投票机制的核心要点：

      • 验证者按质押权重投票，形成投票塔结构
      • 投票塔中锁定期指数级增长(1, 2, 4, ..., 2^31)，32 次投票后达到最大锁定期 (2^32)
      • 乐观确认是最终确认 32 次中的第 1 次投票，两者是包含关系，非独立流程
      • 最终确认意味着区块不可逆，攻击成本极高(需> 1/3 质押权益共谋)

      Solana 的 400ms 固定槽位是其高性能共识系统的基石

      • 时间秩序：为网络提供确定性的时间流，确保交易有序处理
      • 去中心化：通过领导者轮换 (每 400ms) 防止权力集中
      • 快速确认：400ms 出块时间 + 指数级投票锁定，实现 12.8 秒最终确认
      • 高吞吐量：每个槽位可处理数千交易，支撑 Solana 的高性能表现

  3. Rotor--https://www.anza.xyz/alpenglow-1-1

    • 核心定位：负责“数据传播优化”的核心组件，专注解决区块链网络中最关键的“如何高效传输区块数据”问题。替代原POH的时间戳调度逻辑。替代原Turbine的多层树状200+跳。
    • 地层逻辑：
      • 单跳中继架构：采用 "一跳分片传播"，数据直接从源节点经专用中继发送到目标节点，跳过传统多跳 gossip，减少 40% 带宽消耗，与90%+网络跳数
      • 分片-编码-重组：将区块拆分为多个数据片段，每个片段使用纠删码(Erasure Coding)编码。即使部分节点离线或数据包丢失，只需要50%片段即可完成整重建原始区块。分片大小与数量动态调整，适配不同网络条件与区块大小。
      • 质押权重导向：中继节点选择和带宽分配基于验证者的质押权重。高质押验证者承担更多传播责任，获得更多带宽资源。确保“更大贡献者获得更大影响力”，与PoS共识经济模型一致。
      • 时间戳优化：内置轻量级时间同步机制，替代原 PoH 的递归哈希时间戳，降低计算开销，同时保持事件顺序验证能力
      • 确定性传播：每个区块传播路径在生成前已确定，形成固定的“传播树”。所有节点严格遵循预定义的传播顺序，确保全网状态一致。结合固定400ms槽位时间，实现时间与空间的精确同步。

  4. Votor--https://www.anza.xyz/alpenglow-1-1

    • 核心定位：新一代高效拜占庭容错共识引擎，负责区块最终性确认和投票决策。采用20+20容错模型，将共识活动从链上移至链下。“投票与区块最终性”的核心组件，通过革命性的直接投票机制代替TowerBFT，实现亚秒级确认。

    • 地层逻辑：

      一、核心定义与结构

      Votor 的 "20+20 容错模型" 是 Alpenglow 共识协议的核心安全机制，它将网络故障分为两类并分别提供保障：

      • 拜占庭故障 ≤ 20%: 当最多 20% 的质押权益被恶意验证者控制时，安全性(链的一致性) 仍然成立
      • 非恶意现象 ≤ 20%: 当最多 20% 的质押权益 (与恶意权益分开) 离线或无响应时，活跃性(链的持续运行) 仍然成立

      关键特性: 这两个 20% 是独立计算的，意味着网络总共可容忍40% 的异常验证者(20% 恶意 + 20% 离线)，仍能正常工作

      二、安全性保障机制 (拜占庭故障≤20%)

      安全性是指区块链不会产生错误状态 (如双花)，即使面对恶意攻击:

      1. 防御原理
      • 降低拜占庭容错阈值: 从 Tower BFT 的 33% 降至 20%，使攻击成本更高
      • 基于 "5f+1" 理论: 源自分布式系统经典论文，确保在 f 个故障节点存在时仍能达成共识
      • 投票权重保护: 验证者投票权重与其质押权益成正比，恶意节点即使控制 20% 权益，也无法主导投票
      1. 具体防御措施
      • 双重验证: 区块需获得 **≥80% 权益批准 **(单轮) 或 **≥60% 权益两轮批准 ** 才能最终确认，使恶意节点难以操纵结果
      • 冲突检测: 两个冲突区块无法同时获得最终确认，因为它们的权益投票会重叠，系统会识别并拒绝
      • BLS 聚合签名: 将多个验证者签名聚合成单个证书，便于快速验证，同时增加恶意节点伪造难度
      • 可证明作弊: 恶意验证者若对冲突区块双重签名，其行为将被全网识别，可能导致质押被罚没

      三、活跃性保障机制 (非恶意现象≤20%)

      活跃性是指网络能持续生成和确认区块，即使部分节点离线或响应缓慢:

      1. 网络弹性设计
      • 分层投票策略:
        • 快速路径：首轮获 **≥80% 权益 ** 支持，100ms 内完成确认
        • 慢速路径：首轮60-80% 权益支持，启动第二轮，两轮均达 ≥60%，150ms 内完成确认
        • 两种路径并行执行，先满足条件者生效
      • 单跳传播: Rotor 组件采用单层中继节点，将区块传播延迟控制在 ≤150ms，减少离线节点影响
      • 本地超时机制: 每个验证者独立计时，无需依赖全局时钟 (替代原 POH)，提高抗干扰能力
      1. 离线处理机制
      • SkipVote 机制: 当 leader 未能及时生成区块或分片超时，验证者可发送 SkipVote，若 **≥60% 权益 ** 投 SkipVote，该 slot 将被正式跳过
      • 窗口管理: leader 负责 4 个连续 slot 窗口，若第一个 slot 失败，整个窗口将被标记为无效，避免长时间等待
      • 投票激励: SkipVote 与正常投票获得相同奖励权重，鼓励验证者在异常情况下仍积极参与

      四、20+20 模型工作流程详解

      场景 1: 网络正常 (恶意 < 20%，离线 < 20%)

      1. Leader 生成新区块并广播
      2. 验证者通过 Rotor 快速接收 (≤150ms)
      3. 首轮投票: ≥80% 权益批准→快速确认(100ms)
      4. 区块成为 "root"(根区块)，链继续扩展

      场景 2: 部分节点离线 (离线≈20%)

      1. 首轮投票：获65% 权益批准 (未达 80% 但≥60%)
      2. 系统立即启动第二轮投票
      3. 第二轮：再次获 **≥60% 权益 ** 批准→最终确认(150ms)
      4. 即使部分节点离线，共识仍能达成

      场景 3: 存在恶意节点 (恶意≈20%)

      1. 恶意节点试图对冲突区块双重投票
      2. 诚实节点检测到冲突签名，拒绝确认恶意区块
      3. 恶意行为被记录，可能触发惩罚机制
      4. 网络继续在诚实链上达成共识

      五、为什么选择 "20+20" 这个数字？

      • 安全性权衡: 20% 是在安全性与性能间取得的平衡，比传统 BFT 的 33% 更严格，大幅提升攻击难度
      • 数学证明: 基于 Martin 和 Alvisi 的 "5f+1" 理论，在 f=20% 时，系统仍能保证:
        • 安全性：恶意节点无法使诚实节点接受错误区块
        • 活跃性：诚实节点最终能就某区块达成一致
      • 性能考量: 两个 20% 的设计使 Votor 能在100-150ms内完成确认 (相比 Tower BFT 的 12.8 秒)，同时保持高容错

      六、与 Tower BFT 容错模型对比

      特性Tower BFTVotor 20+20 模型
      恶意节点容忍33%20%(更严格)
      离线节点容忍无专门保障20%(独立保障)
      确认时间约 12.8 秒100-150ms(提升 80 倍)
      投票轮数多轮最多两轮(通常一轮)
      通信模型gossip 广播直接点对点 + 单跳传播

      七、总结

      Votor 的 20+20 容错模型是 Alpenglow 共识的核心创新，它通过精确区分并独立处理两类网络故障，在保持高安全性的同时实现了前所未有的性能提升:

      • 安全性: 最多容忍 20% 恶意验证者，确保区块链不产生错误状态
      • 活跃性: 最多容忍 20% 离线验证者，确保网络持续运行
      • 性能: 将确认时间从 12.8 秒缩短至 100-150ms，支持 Solana 处理更高吞吐量

      核心优势: 即使在 40% 验证者异常的极端情况下 (20% 恶意 + 20% 离线)，Solana 网络仍能保持安全、稳定运行，为大规模去中心化应用提供了坚实基础。

  5. 涡轮协议---Turbine

    • 核心定位：区块传播优化协议，降低带宽消耗、加速数据同步。
    • 地层逻辑：将区块数据分割为小块并行传输，验证节点按需接收并转发，大幅缩短区块在全网的传播时间，提升交易确认速度。

  6. 湾流协议---Gulf Stream

    • 核心定位： 无内存池交易转发机制，减少交易处理延迟。
    • 地层逻辑： 验证着提前预判并预处理待确认交易，交易提交后无需等待内存池排队，直接进入处理流程，缩短从提交到执行的耗时。

  7. 海平面引擎---Sealevel

    • 核心定位： 并行智能合约执行引擎，突破串行执行的性能瓶颈。
    • 地层逻辑：支持同一区块内数千个智能合约并行运行，充分利用多核硬件算力，同时适配GPU、SSD资源高效利用，直接提升网络交易吞吐量。

  8. 流水线技术---Pipelining

    • 核心定位：硬件级交易验证优化，实现交易连续处理。
    • 地层逻辑：将交易验证拆解为“接收-验证-执行-记账”多个阶段，不同硬件单元并行处理不同阶段任务，避免单阶段拥堵，提升整体处理效率。

  9. 云裂架构---Cloudbreak

    • 核心定位：水平扩展账户数据库，值乘大规模并发读写。
    • 地层逻辑：采用多线程并行读写设计(支持32线程)，将账户数据分布式存储于多个节点，实现性能随节点数量线型扩张，应对海量账户操作请求。

  10. 存档器---Archivers

  • 核心定位：去中心化历史数据存储方案，降低主网性能损耗。
  • 地层逻辑：独立节点集群存储区块链历史数据，主网节点无需承担全量存储压力，且普通笔记本即可作为存档节点，降低网络维护门槛，保障数据安全性与可追溯性。

Solana名词概念

  1. accounts

    All data on the Solana blockchain is stored as an Account.The structure of the Solana blockchain resembles a key-value store, in which the key is the on-chain address and the value is an Account.

    A record in the Solana ledger that either holds data or is an executable program.

    Like an account at a traditional bank, a Solana account may hold funds called lamports. Like a file in Linux, it is addressable by a key, often referred to as a public key or pubkey.

    The key may be one of:

    • an ed25519 public key
    • a program-derived account address (32byte value forced off the ed25519 curve)
    • a hash of an ed25519 public key with a 32 character string

  2. smart contract、validator

  3. blockchain explorer

  4. address

  5. transfer

  6. dApp

  7. token

    Tokens are digital assets that represent ownership over diverse categories of assets. Tokenization enables the digitalization of property rights—a fundamental component for managing fungible and non-fungible assets.

    代币（Tokens）是代表各类资产所有权的数字资产。资产代币化（Tokenization）实现了产权的数字化，这是管理可替代资产（fungible assets）和非同质化资产（non-fungible assets）的核心组成部分。

    • Fungible Tokens: Interchangeable and divisible assets of the same type and value (ex. USDC).
    • Non-fungible Tokens (NFT): Ownership of indivisible assets (e.g. artwork).

  8. fee

    There are three different types of fees that can be incurred when using the Solana blockchain:

    • Transaction Fees: A fee to have validators process transactions & instructions
    • Prioritization Fees: An optional fee to boost a transaction's processing order
    • Rent: A withheld balance to keep data stored on-chain

  9. block

    A contiguous set of entries on the ledger covered by a vote. A leader produces at most one block per slot.

  10. lease

  11. signature

    A 64-byte ed25519 signature of R (32-bytes) and S (32-bytes). With the requirement that R is a packed Edwards point not of small order and S is a scalar in the range of 0 <= S < L. This requirement ensures no signature malleability. Each transaction must have at least one signature for fee account. Thus, the first signature in transaction can be treated as transaction id

  12. wallet

    A collection of keypairs that allows users to manage their funds.

votor多轮投票详解

Votor的多轮投票机制详解

  1. 第一轮投票的核心功能

第一轮投票是Votor共识的"快速通道"，主要功能包括：

  • 区块验证：验证者检查区块有效性（交易合法性、签名等）

  • 快速确认路径：如果第一轮投票获得≥80%的权益支持，区块立即获得"Fast-Finalization Certificate"并最终确认，无需第二轮

  • 双轨启动：即使未达到80%，只要获得≥60%支持，Votor会立即启动第二轮投票，形成"双轨并行"的高效决策机制

  1. 投票轮数控制：固定还是动态？

Votor采用动态轮数控制，而非固定轮数，这是其高效性的关键：

  • 单轮快速路径（理想情况）：

  • 条件：第一轮投票达到≥80%权益支持

  • 结果：区块在100-150ms内完成最终确认，生成Fast-Finalization证书

  • 双轮安全路径（一般情况）：

  • 条件：第一轮60%-80%支持，未达快速确认门槛

  • 过程：立即启动第二轮投票，两轮投票共享相同的初始投票数据

  • 结果：第二轮达到≥60%支持即最终确认，总耗时仍控制在150-200ms内

  • 关键优化：两轮投票并行执行，而非顺序执行，哪个先达到阈值就采用哪个结果，确保在400ms时隙内完成决策

  1. 400ms时隙与投票的关系

400ms是一个"安全时间窗口"，确保：

  • 领导者有足够时间生成区块并全网传播

  • 验证者有足够时间完成区块验证和两轮投票

  • 即使在网络延迟较高的情况下，共识流程仍能在一个时隙内完成

Solana区块大小

一、核心概念：区块容量与计算单元(CU)

Solana的区块"大小"主要以计算单元(Compute Units, CU)衡量，而非传统区块链的字节大小：

当前主网限制：6000万CU/区块（2025年7月通过SIMD-0256提案从5000万CU提升）

计算单元(CU)是什么？

  • 衡量区块内可执行计算工作量的单位
  • 代表"一个区块最多能做多少事"，而非数据存储量
  • 限制领导者能打包进区块的工作量，确保大多数验证者能跟上网络

实际应用：

  • 每个交易默认消耗约20万CU，复杂交易可达140万CU
  • 每个区块平均包含600-1400笔交易，取决于交易复杂度

二、区块的实际字节大小

虽然CU是主要限制，但Solana区块也有最大字节容量：

  • 理论最大：128MB（通过Turbine协议分片技术实现）
  • 实现方式：将区块分解为1280字节的数据包（称为"分片shreds"），由不同验证器并行验证

区块结构：

  • 包含区块头（元数据、哈希值等）
  • 包含交易列表（每个交易最大1232字节）
  • 包含PoH哈希链（Alpenglow前）或逻辑时间戳（Alpenglow后）

三、为什么不用传统字节大小限制？

Solana的创新在于以计算工作量而非数据量定义区块"大小"：

  1. 计算密集型限制：更精准控制区块处理负载，防止资源耗尽攻击
  2. 动态资源分配：同样字节的交易，复杂计算消耗更多CU，简单交易消耗更少
  3. 水平扩展：验证者硬件性能提升时，可通过协议升级增加CU上限（如从5000万→6000万→计划1亿CU）

四、最新发展：区块容量升级提案

目前有两个重要提案正在讨论：

  1. SIMD-0286：将CU上限从6000万提升至1亿（增加66%），已提出但未实施
  2. SIMD-0370：更激进的方案，取消固定CU限制，改为基于验证器硬件性能的动态区块大小，小验证器可跳过超出其容量的区块验证

总结

Solana区块大小通过双重机制控制：

  • 计算单元(CU)限制（当前6000万）：控制区块内计算工作量
  • 字节大小限制（理论最大128MB）：通过分片技术支持大规模数据处理

核心区别：与比特币（约1MB）、以太坊（约30MB）等传统区块链不同，Solana更关注计算资源消耗而非单纯的数据存储量，这是其实现高吞吐量（2000-3000TPS）的关键设计。

计算单元(CU)

一、CU的本质：区块链的"计算卡路里"

计算单元(Compute Units, CU)是Solana衡量交易执行所需计算资源的基本单位，类似于：

  • 汽车的"油耗"(每公里消耗多少升汽油)
  • 手机的"电量"(完成任务消耗多少毫安时)
  • 工厂的"工时"(完成订单需要多少人工小时)

核心定义：1个CU ≈ 33纳秒(0.000000033秒)的计算时间。最小的区块链操作(如简单的算术运算)消耗1个CU，复杂操作消耗更多。

二、为什么需要CU？三大关键作用

1️⃣ 防止"无限循环攻击"

  • 每个交易默认限制20万CU，最多可请求140万CU
  • 当交易执行消耗的CU超过限制时，程序会立即终止并回滚所有状态变更
  • 这保护网络免受恶意合约通过无限循环耗尽所有节点计算资源的攻击

2️⃣ 公平分配区块处理能力

  • 每个区块固定限制6000万CU(2025年7月从5000万CU提升)
  • 就像餐厅一次只能接待一定数量的顾客，CU限制确保：
  • 简单交易(约1000-2000 CU/笔)：一个区块可处理约6万笔
  • 复杂DeFi交易(约10万CU/笔)：一个区块仅能处理约600笔
  • 防止单个复杂交易独占整个区块资源，保证网络公平性

3️⃣ 精确计量与定价

  • 交易费用 = CU价格 × 消耗的CU数量
  • 用户可通过设置更高的CU价格获得优先处理权，类似"加急费"
  • 验证者获得100%的优先费用，作为处理交易的"算力报酬"

三、CU如何工作？一个直观比喻

想象你在一个烹饪比赛中：

  • 厨房 = Solana区块链网络
  • 厨师 = 验证节点(负责处理交易)
  • 烹饪时间 = 计算资源(CU)
  • 菜谱 = 智能合约程序
  • 食材 = 交易数据

规则：

  • 每位厨师一次只能烹饪一道菜(处理一个交易)
  • 比赛总时长固定为6000万秒(相当于区块CU上限)
  • 每道菜必须在20万秒内完成(交易CU上限)，复杂菜最多可申请140万秒
  • 超时的菜会被直接丢弃，食材退回但不退还比赛费用

四、CU的具体数值：交易消耗实例

交易类型 大致CU消耗 相当于 简单转账 1,000-2,000 CU 33-66微秒 智能合约调用(基础) 5,000-20,000 CU 0.16-0.66毫秒 复杂DeFi操作 50,000-140,000 CU 1.6-4.6毫秒 一次区块全部容量 6000万CU 约2秒(理论最大值)

实际应用：Solana主网每个区块平均包含600-1400笔交易，平均CU利用率约85%，表明网络处于高效但不过载的状态。

五、CU vs 传统区块链的"字节大小"

特性 Solana (CU限制) 比特币/以太坊 (字节限制) 衡量对象 计算工作量(执行时间) 数据存储量(字节数) 控制目标 防止计算资源耗尽 防止存储爆炸 资源类型 CPU计算时间 磁盘空间 灵活性 高(复杂交易消耗更多CU) 低(同等字节消耗相同资源) 扩容方式 调整CU上限(如6000万→1亿) 增加区块大小(如1MB→30MB)

关键区别：CU不是限制区块能存储多少数据，而是限制区块能做多少计算。这使Solana能更精准地防止资源滥用，同时允许处理更大的数据集(通过分片技术支持最大128MB区块)。

六、CU的未来：从固定限制到动态调整

目前Solana社区正讨论两项重大变革：

  1. SIMD-0286：将CU上限从6000万提升至1亿(增加66%)，以应对日益增长的DeFi和NFT应用需求
  2. SIMD-0370：更激进的方案，取消固定CU限制，改为基于验证器硬件性能的动态分配，使网络处理能力随硬件进步自然扩展

总结：CU的"三个一"记忆法

一个核心公式：1 CU = 33纳秒计算时间

一个形象比喻：CU是区块链世界的"时间货币"，你需要"支付"一定数量的CU来"购买"区块链为你执行计算的时间

一个关键作用：CU是Solana实现高性能(2000-3000TPS)与安全性平衡的核心机制，确保网络既能快速处理大量交易，又不会被恶意代码攻击瘫痪

一句话理解：CU就是告诉区块链"这个交易我愿意花多少计算时间来处理"，网络根据这个"时间预算"决定是否接受并优先处理你的交易。

注：CU是Solana特有的概念，与其他区块链的Gas(以太坊)或VBC(波场)等资源计量机制有相似之处，但实现原理完全不同。

CU消耗

https://solana.com/developers/guides/advanced/how-to-optimize-compute

在 Solana 上开发时，务必关注程序的计算资源使用量。程序的计算资源消耗不仅会影响用户能获得的最大性能，还会增加包含优先费用（priority fees）的交易执行成本。

优化计算单元（CU）使用量可带来以下好处：

  • 消耗 CU 更少的交易，被打包进区块的概率更高；
  • 低 CU 消耗的指令让你的程序更具可组合性（composable）；
  • 降低区块的整体 CU 占用率，使单个区块能容纳更多交易。

本指南将介绍如何优化程序的计算资源使用，确保其达到最高运行效率。

当前的计算资源限制是什么？

Solana 程序有以下几项需要注意的计算资源限制：

  • 每区块最大 CU：6000 万 CU；
  • 每区块内单个账户最大 CU：1200 万 CU；
  • 单交易最大 CU：140 万 CU。

将程序的 CU 消耗控制在这些限制内，对于确保程序及时执行且成本合理至关重要。尤其当你的程序开始被大量用户使用时，必须尽可能高效地管理 CU 消耗，避免触及 “单账户每区块最大 CU” 上限。

如何测量 CU 消耗？

在开发 Solana 程序时，你需要检查程序不同部分的 CU 消耗情况。可以使用compute_fn宏来测量不同代码片段的 CU 使用量。

通过以下代码测量 CU 消耗：

compute_fn!("自定义提示信息" => {
    // 待测量的代码
});

该宏的输出会显示代码执行前后的 CU 消耗差值，帮助你定位程序中最耗 CU 的部分。你可以在cu_optimizations仓库中找到该宏的使用示例。

程序优化技巧

日志输出（Logging）

虽然日志是理解程序内部运行状态的有效方式，但日志输出的 CU 消耗极高。应避免在程序中打印非必要信息，以降低 CU 占用。

例如，base58 编码和字符串拼接都是高耗 CU 操作：

// 消耗11962 CU！！
// base58编码和字符串拼接均为高耗CU操作
compute_fn! { "打印账户公钥（低效方式）" =>
    msg!("A string {0}", ctx.accounts.counter.to_account_info().key());
}

// 消耗357 CU——仅字符串拼接就很耗CU
compute_fn! { "简单拼接打印公钥" =>
    msg!("A string {0}", "5w6z5PWvtkCd4PaAV7avxE6Fy5brhZsFdbRLMt8UefRQ");
}

如果确实需要打印公钥，可使用.key() + .log()方法高效打印，降低 CU 消耗：

// 仅消耗262 CU
compute_fn! { "高效打印公钥" =>
    ctx.accounts.counter.to_account_info().key().log();
}
数据类型（Data Types）

更大的数据类型整体会消耗更多 CU。使用u64等大尺寸数据类型前，务必确认是否真的需要 —— 相比u8等小数据类型，大尺寸类型的 CU 消耗会显著更高。

// 消耗357 CU
compute_fn! { "向量中存储u64类型" =>
    let mut a: Vec<u64> = Vec::new();
    a.push(1);
    a.push(1);
    a.push(1);
    a.push(1);
    a.push(1);
    a.push(1);
}

// 仅消耗211 CU
compute_fn! { "向量中存储u8类型" =>
    let mut a: Vec<u8> = Vec::new();
    a.push(1);
    a.push(1);
    a.push(1);
    a.push(1);
    a.push(1);
    a.push(1);
}

整体来看，数据类型的差异会在整个程序中累积，导致 CU 消耗大幅增加。

序列化（Serialization）

根据账户结构体的复杂度，序列化和反序列化操作的 CU 消耗会很高。如果可能，应使用 “零拷贝（zero copy）” 技术，直接操作账户数据，避免这些高耗 CU 操作。

// 消耗6302 CU（含序列化开销）
pub fn initialize(_ctx: Context<InitializeCounter>) -> Result<()> {
    Ok(())
}

// 消耗5020 CU（零拷贝，无序列化开销）
pub fn initialize_zero_copy(_ctx: Context<InitializeCounterZeroCopy>) -> Result<()> {
    Ok(())
}

// 消耗108 CU——含序列化总CU为2600
let counter = &mut ctx.accounts.counter;
compute_fn! { "Borsh序列化" =>
    counter.count = counter.count.checked_add(1).unwrap();
}

// 消耗151 CU——含序列化总CU为1254（节省约50%）
let counter = &mut ctx.accounts.counter_zero_copy.load_mut()?;
compute_fn! { "零拷贝序列化" =>
    counter.count = counter.count.checked_add(1).unwrap();
}

通过上述示例可见，在程序中使用零拷贝技术，有望节省高达 50% 以上的总 CU 消耗。

程序派生地址（Program Derived Addresses, PDAs）

使用程序派生地址（PDAs）是 Solana 程序中的常见做法，但需注意find_program_address的 CU 消耗，并掌握优化方法。

如果find_program_address需要多次尝试才能找到有效地址（即 bump 值较小），整体 CU 消耗会很高。优化方案：初始化后将 bump 值存储到账户中，后续直接复用该 bump 值。

pub fn pdas(ctx: Context<PdaAccounts>) -> Result<()> {
    let program_id = Pubkey::from_str("5w6z5PWvtkCd4PaAV7avxE6Fy5brhZsFdbRLMt8UefRQ").unwrap();

    // 消耗12,136 CU（未复用bump，需多次尝试）
    compute_fn! { "查找PDA（低效）" =>
        Pubkey::find_program_address(&[b"counter"], ctx.program_id);
    }

    // 仅消耗1,651 CU（直接使用已知bump，无需尝试）
    compute_fn! { "查找PDA（高效）" =>
        Pubkey::create_program_address(&[b"counter", &[248_u8]], &program_id).unwrap();
    }

    Ok(())
}

#[derive(Accounts)]
pub struct PdaAccounts<'info> {
    #[account(mut)]
    pub counter: Account<'info, CounterData>,
    // 未指定bump：消耗12,136 CU
    #[account(
        seeds = [b"counter"],
        bump
    )]
    pub counter_checked: Account<'info, CounterData>,
}

#[derive(Accounts)]
pub struct PdaAccounts<'info> {
    #[account(mut)]
    pub counter: Account<'info, CounterData>,
    // 复用账户中存储的bump：仅消耗1600 CU
    #[account(
        seeds = [b"counter"],
        bump = counter_checked.bump
    )]
    pub counter_checked: Account<'info, CounterData>,
}

更多 CU 优化方向

还有许多其他优化程序 CU 消耗的方法，例如使用原生代码（native）而非 Anchor 框架开发 —— 但这些方法都需要权衡开发效率。如果追求程序极致的 CU 性能，建议评估并测试不同方案，找到最适合自身业务场景的优化方式。

文档核心内容详细讲解（技术原理 + 实操价值）

结合你之前关注的 “CU 本质（SVM 字节码计量）”，本次文档的核心是 “如何通过代码优化减少 SVM 指令执行次数，从而降低 CU 消耗”，以下分模块拆解：

1. 先明确 3 个关键前提（文档核心限制）
  • 每区块 6000 万 CU：是当前 Agave 版本的硬限制（比旧版提升 20%），意味着单个区块内所有交易的 CU 总和不能超 6000 万 —— 你的程序 CU 消耗越低，越容易在网络拥堵时被打包；
  • 单账户每区块 1200 万 CU：是 “账户级限流”，避免热门账户（如热门 NFT 合约）占用过多区块资源，导致其他用户交易失败；
  • 单交易 140 万 CU：是 “交易级上限”，默认 20 万 CU，可通过ComputeBudgetInstruction::set_compute_unit_limit手动提升到 140 万，但越高的 CU 意味着越高的交易费。
2. 五大优化技巧：原理 + 实操（结合 SVM 指令逻辑）
（1）日志输出优化：最容易踩的 “CU 陷阱”
  • 原理：msg!宏的 CU 消耗高，核心是两个 SVM 指令开销：
    1. 字符串拼接 / 格式化：需要执行CONCAT（拼接）、FORMAT（格式化）等指令，每个指令消耗 10-100 CU；
    2. base58 编码：打印公钥时，默认会将Pubkey类型转成 base58 字符串，需执行BASE58_ENCODE指令（消耗 1000+ CU）。
  • 实操建议：
    • 非调试场景禁用所有冗余日志；
    • 必须打印公钥时，用.key().log()替代msg!—— 直接调用 SVM 的LOG_PUBKEY指令（仅 262 CU），跳过编码和拼接步骤。
（2）数据类型优化：小类型 = 少指令 = 低 CU
  • 原理：SVM 处理大尺寸数据类型时，需要更多指令：
    • u8（1 字节）：读取 / 写入仅需 1 条LOAD/STORE指令（10/100 CU）；
    • u64（8 字节）：读取 / 写入需要分多次指令（或更复杂的内存操作），CU 消耗几乎是u8的 2 倍。
  • 实操建议：
    • 能用u8绝不选u64（比如计数器、状态标记等）；
    • 复杂结构体中，将小字段聚合存储，减少内存访问次数。
（3）序列化优化：零拷贝 = 跳过 “编码 / 解码” 指令
  • 原理：
    • 普通序列化（如 Borsh）：需要执行SERIALIZE/DESERIALIZE指令，将 Rust 结构体转成字节流（消耗 1000+ CU）；
    • 零拷贝（zero copy）：直接映射账户内存到程序地址空间，无需编码 / 解码，仅需LOAD/STORE指令（10-100 CU）。
  • 实操建议：
    • 使用 Anchor 的#[account(zero_copy)]宏标记账户结构体；
    • 注意：零拷贝要求账户数据对齐（如#[repr(C)]），且不能直接使用复杂嵌套类型（如Vec），需手动管理内存。
（4）PDAs 优化：复用 bump = 减少 “尝试性指令”
  • 原理：
    • find_program_address：为了找到有效 PDA，会从 bump=255 开始反向尝试，直到找到不落在 Ed25519 曲线上的地址 —— 每次尝试都要执行ECP_SECP256K1_VERIFY（椭圆曲线验证）指令（1000+ CU / 次），bump 越小，尝试次数越多，CU 消耗越高；
    • create_program_address：直接使用已知的 bump 值，仅需 1 次验证指令（1651 CU），无需反复尝试。
  • 实操建议：
    • 初始化 PDA 时，将找到的 bump 值存储到账户中（如counter_checked.bump）；
    • 后续使用 PDA 时，直接从账户中读取 bump，调用create_program_address。
（5）进阶优化：原生开发 vs Anchor
  • 原理：Anchor 框架为了简化开发，封装了很多通用逻辑（如序列化、账户验证），但这些封装会引入额外的 SVM 指令（CU 消耗）；
  • 实操建议：
    • 高频调用的核心程序（如 DEX 核心合约）：用原生 Rust 开发，手动控制每一条 SVM 指令，极致优化 CU；
    • 普通应用程序：优先用 Anchor（开发效率高），仅对核心路径（如交易执行、状态更新）做零拷贝、日志优化等关键优化。
3. 测量 CU 消耗的核心工具：compute_fn宏
  • 原理：该宏会在代码执行前后，调用 SVM 的GET_COMPUTE_UNIT_CONSUMED指令，获取当前 CU 消耗值，两者差值就是目标代码的 CU 消耗；
  • 实操步骤：
    1. 安装依赖：cargo add solana-compute-meter；
    2. 在代码中插入compute_fn!宏，包裹待测量的代码片段；
    3. 运行测试：cargo test-sbf，查看输出中的 CU 消耗数值；
    4. 定位高耗 CU 代码，针对性优化。
4. 优化效果量化（文档示例对比）
优化场景优化前 CU 消耗优化后 CU 消耗节省比例
打印公钥（msg!→.log()）11962 CU262 CU97.8%
向量存储（u64→u8）357 CU211 CU41%
账户初始化（普通→零拷贝）6302 CU5020 CU20.3%
PDA 查找（find→create）12136 CU1651 CU86.4%

总结：CU 优化的核心逻辑

所有优化技巧的本质都是 “减少 SVM 指令执行次数”—— 因为 CU 是按 SVM 字节码指令计量的，每少执行一条高耗 CU 指令，总消耗就会降低。

核心优化思路：

  1. 避免冗余操作（如冗余日志、重复序列化）；
  2. 用高效指令替代低效指令（如LOG_PUBKEY替代BASE58_ENCODE + CONCAT）；
  3. 复用计算结果（如存储 PDA 的 bump 值，避免重复尝试）；
  4. 小数据类型 + 零拷贝，减少内存操作指令。

这些优化不仅能降低交易费，还能让你的程序在 Solana 高吞吐量网络中更稳定（避免因 CU 超限被拒绝打包），尤其适合面向北美远程工作场景中的高并发应用开发需求。

SPL

SPL 是 Solana 区块链的代币标准，你可以把它理解为一套官方制定的“代币游戏规则”。它规定了代币如何创建、转账和管理，确保了所有基于 Solana 的代币都能被钱包、交易所和各种应用（DApp）无缝识别和处理-2。

Solana Token standard

标准名称 (SPL)等效以太坊标准核心用途备注
SPL TokenERC-20同质化代币。如：USDC, USDT, SOL 的 Wrapped 版本。最基础、最核心的代币标准。您提到的 ATA 就是基于此标准的一个账户生成规范，用于为每个用户安全地生成一个唯一的接收地址。
SPL Token-2022ERC-20 升级版功能增强的同质化代币。在 SPL Token 基础上增加了原生功能，如：转账手续费、保密转账、不可转让代币等。是 SPL Token 的升级版，旨在不破坏兼容性的情况下引入新功能。
Metaplex NFTERC-721 / ERC-1155非同质化代币 (NFT) 和 半同质化代币 (SFT)。虽然技术上基于 SPL Token，但 Metaplex 协议为 NFT 定义了元数据（如图片、属性）、创建、销售等一整套规则，是 Solana 上事实上的 NFT 标准。
Programmable NFT (pNFT)无直接等效可编程 NFT。为 NFT 添加了复杂的规则，如：强制执行版税、限制转移等。在 Metaplex NFT 基础上的重大升级，解决了版税难执行等问题。

  1. SPL Token 是基石：所有代币，无论是同质化的 USDC 还是非同质化的 NFT，其底层账户模型都遵循 spl-token 程序规则。这确保了钱包和浏览器能统一识别。

  2. ATA 是什么？：它不是一个独立的代币标准，而是 SPL Token 标准下的一个最佳实践。它的全称是“关联代币账户”，其核心价值是：

    • 确定性：通过你的钱包地址和代币地址，就能算出一个唯一的接收地址。
    • 防丢失：避免了用户为同一种代币创建多个账户，导致不知道哪个里有币。
    • 方便：成为 DApp 和钱包默认的找零和接收地址。
    特性关联代币账户 (ATA)非关联代币账户
    地址生成确定性 PDA，由 (owner, token_program, mint) 推导随机密钥对，公钥作为地址
    私钥无（是PDA，由程序控制）有（是密钥对，需要安全存储）
    创建方式通过关联代币程序 create_associated_token_account通过系统程序 create_account + 代币程序 initialize_account
    查找知道 owner 和 mint 即可算出需要记录或扫描链上数据
    使用场景标准做法，用于接收代币、空投特殊场景，如需要为同一个代币创建多个账户（做税务隔离）、或某些需要自定义所有权的复杂程序逻辑

  3. 为什么是 Metaplex？： Solana 基金会定义了基础的 SPL Token 标准（相当于规定了“纸”怎么做），而 Metaplex 这个社区项目定义了 NFT 的具体格式（相当于规定了“钞票”的图案、防伪等）。所以，在 Solana 上聊 NFT，几乎就等于在聊 Metaplex 标准。

  4. Token-2022 是未来：它就像一个有各种插座的升级电源，想要加什么功能（如转账扣费）就直接插上，而无需再单独造一个新的电源。这是 Solana 代币为了适应更复杂金融场景的进化。

如果有人问“Solana 的 SPL 代币标准有哪些”，最直接的回答是：

  • FT：看 SPL Token 和它的升级版 SPL Token-2022。
  • NFT：看 Metaplex NFT 和 Programmable NFT (pNFT)。
  • ATA：是上述所有标准在使用过程中，为了管理代币账户而衍生出的一个关键地址生成方案。

命令行获取SPL代币账户地址

1. 获取关联代币账户（ATA）地址

# 计算特定用户对特定代币的ATA地址
spl-token address --owner <用户钱包地址> --token <代币Mint地址>

# 示例
spl-token address --owner 7x1K... --token EPjFW...USDC
# 输出: 6X4F... (用户的USDC ATA地址)

2. 列出用户的所有代币账户

# 列出用户持有的所有代币账户（包括ATA和非ATA）
spl-token accounts --owner <用户钱包地址>

# 输出示例：
# Account                                      Token Mint                           Balance
# 6X4F...                                      EPjFW...USDC                         100.00
# 8Y2H...                                     Mango...MNGO                          50.00

3. 查看特定代币账户详情

# 查看代币账户的详细信息
spl-token account <代币账户地址>

# 输出包含：
# - Address: 账户地址
# - Mint: 对应的代币Mint
# - Owner: 账户所有者
# - Amount: 余额
# - Delegation: 委托信息

4. 查找代币的所有持有者

# 查找特定代币的所有持有者账户
spl-token accounts --token <代币Mint地址> --output json

# 这会列出所有持有该代币的账户地址和余额

规则核心提炼：

  1. SPL Token：定义了代币的原子操作（创建、转账、授权）和基础双权限。
  2. Token-2022：在原子操作上增加了功能模块（如利息、转账费、元数据指针），并引入了更强的控制权限（永久委托）。
  3. Metaplex NFT：在SPL Token基础上增加了描述层（元数据） 和收益分配规则（版税、创作者列表）。
  4. Programmable NFT (pNFT)：在NFT上增加了状态机（锁定/解锁） 和基于角色的委托系统，使NFT具有可编程行为。

    pub executable: bool,
}
